## 0. 一期目标汇总（本轮审阅入口）

本节功能方向已随用户“其他按建议”采纳；教材确定暂缓、内容分批开放以最新决定为准。具体样题、实现细节和实测结果不因此视为已经验收。

### 0.1 建议的一期交付目标

让自家及身边家长从当前整理的四年级候选知识清单中，选择已开放的训练内容与三档难度，生成正确、可打印、可再次打开的练习；管理员能够逐个维护、检查并发布模板。教材版次暂缓，目录仅作候选分类，不宣称已与某版教材完整同步。

一期有两条必须同时完成的流程：

- 家长：选择候选册次/主题与已开放训练范围 → 设置练习 → 生成 → 预览 → 打印 → 查看历史/重新打印。
- 管理员：维护教材映射/知识点 → 配置模板 → 样题预览与校验 → 审题 → 发布 → 定位错误并停用/回退。

### 0.2 功能范围建议

| 模块 | 一期建议交付 | 暂不纳入一期的建议 |
| --- | --- | --- |
| 内容 | 沿用四年级上下册候选知识目录；模板逐个整理、分批开放；教材映射待核 | 其他年级、多学科、真题采集 |
| 出卷 | 三档难度、题量、知识点选择、适用题型、同卷去重、失败提示 | 自适应推荐、在线考试评分、自动错题追踪 |
| 预览与输出 | 题目、必要图形、答案/关键步骤、答题留白、A4打印、后端生成保存PDF及下载 | 小程序、手机到电脑的身份同步 |
| 历史 | 凭有效匿名身份查看本人试卷快照、重复打印 | 跨设备同步与公开分享 |
| 内容后台 | 教材/知识点维护、模板受控编辑、预览、验证、发布、停用/回退 | 在线编写任意算法、复杂可视化编辑器、多人审批 |
| 管理与运营 | 管理员登录、生成记录、基础概览、必要操作记录 | 完整报表、角色权限体系、支付运营 |
| 数据设计 | 全期实体关系、数据字典、对象契约、各期启用标记；当前功能相关表与关系完整设计 | 不将“表已设计”算作未来功能已经实现 |

后台不是只读的统计后台：如果一期要自己持续补题，模板的受控编辑与发布属于一期实际需求。新算法仍由代码开发，不能承诺所有未来题型都只改配置即可上线。

### 0.3 出题覆盖的验收单位

建立“知识点/训练目标 × 难度 × 适用题型”清单，每项标记：未整理、待核教材、待做模板、待验证、已开放。目录数量与可出题数量分别统计。

三档难度已经确认；建议每个首批开放的训练包都有三档可用内容，但不强制每个原子知识点都凑出三档×所有题型。例如简单概念辨认可在同单元组合训练中形成挑战，不能直接换成未选择的知识点。采用此覆盖原则，具体难度与教学适配仍需通过逐模板样题审查。

已选择分批开放，不以全册覆盖为一期门槛。沿用当前候选清单，先整理多位数乘法模板，再推进数量关系、小数、几何与统计；每批列出实际开放能力，不能把目录录入数当作出题覆盖数。教材暂未核验不阻塞独立知识点模板的整理和开放，但不得宣称与某版教材同步。

### 0.4 本轮不要求用户逐项选择的技术细节

教材与知识点分离、模板不可变版本、试卷内容快照、服务端身份与归属校验、生成幂等、精确数值计算、受控图形生成、发布验证、备份恢复，作为建议技术基线一起审阅，不拆成十几个确认问题。

详细设计采用 Vue 用户端/后台 + FastAPI + SQLAlchemy + SQLite，生成任务由独立worker处理；基础小学运算优先使用明确规则和精确数值表示，SymPy 按需使用，不作为所有模板的必需引擎。服务器配置、成本和时间约束明确后，再定技术部署方案；本轮不开展实现或性能验证。

## 1. 对项目的理解

原稿描述的核心是：为家长生成适合孩子当前学习内容的数学练习，预览后打印，孩子在纸上完成，家长拿参考答案核对。

建议定位：**按知识点生成可打印的数学练习，提供独立的参考答案页。**

“不提供即时答案”建议改成“不做拍照搜题和在线答疑”。前者容易被理解为没有答案，与原稿的答案页冲突。

需要先验证的不是后台统计是否丰富，而是：目标家长是否经常需要额外练习、现有材料哪里不合用、是否有打印条件、生成题是否值得再次使用。原稿对竞品的概括未调研，不作为差异化已成立的证据。

## 2. 当前设计注意事项

本节只保留适用于四年级练习生成的设计问题。原始 V1 文档仅作为历史资料，不再作为内容范围和题量规则依据。

| 问题 | 影响 | 建议 |
| --- | --- | --- |
| 以可用模板数量限制题量 | 一个参数化模板可以产生多题，2 个模板不等于只能出 2 道题 | 区分模板覆盖、合法参数空间、同卷重复限制和已验证最大题量 |
| 6–9 个模板，同时承诺三难度×三题型 | 总数不能证明每个组合都可用 | 建覆盖矩阵，先确定支持组合，不支持的组合隐藏或明确提示 |
| 不足时跨难度补充 | 用户选的难度失效，标记 actual_difficulty 不能替代同意 | 严格按配置生成；不足时返回可行调整，不静默改变难度或题型 |
| ≤12 题保证 1–2 页 | 解答题需要书写空间，综合题和答案解析长度也不固定 | 优先可读性和答题留白；题目页、答案页分开计算页数，不按题数承诺总页数 |
| nextTick 被当作打印就绪兜底 | DOM 更新不等于字体加载、公式渲染和排版完成 | 就绪条件包含数据、公式、所用字体和布局；错误时阻止打印并提示重试 [S2] |
| 统计 browser_print/save_pdf 为真实下载 | 浏览器打印预览关闭不代表打印成功，也无法据此区分保存 PDF | 一期统一记录 print_intent；不宣称真实打印量或 PDF 下载量 [S1] |
| 点击打印即生成 file(print_snapshot) | 用户现已确认后端生成PDF，需独立文件生成链路 | 按同一快照生成PDF并保存file_asset；重新打印/下载读取已有文件 |
| 前端 UUID → X-Client-Id → 用户，与匿名 JWT 并存 | 缺少签发与续期流程；客户端自报 ID 不能作为访问历史的凭证 | 服务端建立匿名身份并签发凭证；UUID 至多作为辅助标识，不凭它找回账号 |
| 微信登录更新同一用户即“零迁移” | 多浏览器、多设备、已有微信账号会产生合并冲突 | 保持内部 user_id 稳定；二期设计绑定、归属证明、合并与冲突处理，不承诺零迁移 |
| admin_user 被列为三期不写入表 | 一期后台登录依赖管理员凭证 | 若一期有后台，管理员账户初始化、登录和失效机制必须同期实现 |
| 全表软删除等同于审计 | 软删除不会记录谁改了什么，也不会自动清理日志 | 按表定义保留、删除和必要操作记录；不对所有表统一软删除 |
| 同时聚合 paper 与 download 容易重复计数 | 多条一对多关联相乘，后台数据被放大 | 分别按用户/知识点聚合后再关联；以明确事件口径验算 |
| SQLite WAL 模式每日直接 cp 主文件 | 可能漏掉 WAL 内已提交事务 | 用 SQLite 在线备份接口或其他一致性备份方式，并做恢复验证 [S3][S4] |
| 周活 20 或累计 500 次触发 PostgreSQL 迁移 | 累计次数无法说明并发写入压力 | 依据锁等待、持续写入并发、接口延迟和运维需求评估；先定位瓶颈 [S5] |
| 固定宣称 170–230MB、1C1G 余量充足 | 未包含实际生成峰值、OS 与其他进程，缺少测量 | 1C1G 作为待验证约束，记录峰值内存和耗时；SymPy 运算并发必须受控 [S6] |
| 一边“不做 monorepo”，一边画出同仓三应用 | 工程独立与仓库独立混淆 | 明确是三个独立构建目录，还是三个 Git 仓库；不为一期引入额外仓库管理工具 |
| 固定四周完成，未提供每周投入时间 | 排期无依据，后台与挑战题占用容易被忽略 | 先确认投入时间，再按可验收里程碑估算 |
| 将小程序、备案、升级规格写成必然路线 | 依赖平台条件和部署路线，当前未核实 | 作为后续待调研事项；不把“已备案二级域名”视为已验证兜底方案 |

## 3. 建议的一期边界

### 3.1 用户闭环

打开网站 → 选择训练内容和题量 → 生成试卷 → 检查预览 → 打印题目页/答案页 → 同一浏览器再次打开历史试卷。

按当前四年级候选目录选择册次/主题与训练知识点，再选择难度，勾选题型并分别设置题数。各题型数量直接显示，总题量自动汇总；只开放已有通过验证模板的组合。教材版次暂缓，目录录入与可出题状态分开显示。

### 3.2 已定边界与后台选项

一期保留三档难度；表与数据对象按全部规划功能统筹设计。用户已确认后台同样全期设计、一期按需实现，不再把“三档难度+完整后台”作为捆绑选项。具体页面以实际内容维护闭环确定。

### 3.3 建议保留与延后

保留：出卷页、预览页、历史记录、使用与隐私说明；本地浏览器打印；参考答案与必要解题步骤；生成失败的清晰提示。

一期后台建议为：登录、教材/知识点映射维护、模板配置/预览、验证/发布/回退、生成记录、概览与最小操作记录。概览看生成成功数、失败数、匿名身份数、打印按钮点击数。

建议延后：丰富统计、无实际文件的文件列表、复杂可视化编辑器、在线编写任意算法、多人审批和 RBAC。已有生成器支持的模板参数与文案编辑，纳入一期维护能力建议。

非目标建议沿用：拍照搜题、在线答疑、支付、真题爬虫、错题本、小程序、多人管理权限。

## 4. 出卷规则建议

- 已确认：按题型分别选题数，初始提供 3/6/8/10/12 档，后续可配置扩展；“等”不解释为必须开放任意整数输入。
- 总题量由各题型数量相加得到，不单独设置，不再使用总量固定 10 或 5/3/2 分布规则。例如选择 3、填空 6、解答 8，共 17 题。
- 交互建议：不选某题型即该项为 0，至少选择一种题型；勾选后默认 3 题（助手默认值，用户未指定）。数量按已有 choice/fill/answer 分类记录，口算、竖式、应用、作图等另作为呈现/训练形式，不隐式重复计数。
- 同一题型跨多个所选知识点分配，其数量表示该题型整卷数量，不是每个知识点各生成这么多。分配明细可预览。
- 能力配置按题型返回可用数量档；开放档位依据当前难度、知识点、已发布模板和同卷去重验证。超出能力明确提示，不自动改档或跨难度补齐。
- 请求对象以 question_type_counts（如 choice=3、fill=6、answer=8）为唯一输入数量来源；总题量服务端计算。若同时保存总数，只作为一致性校验的派生值，不维护两个独立可编辑总数。
- 后台可配置每题型的数量档与默认值；试卷保存实际数量快照。多题型组合可超过 12 题，按总内容自然分页，不能沿用“整卷最多 12 题”的限制。
- 每个难度与题型组合明确可用模板、参数边界和最大已验证题量。`capacity` 返回的是能力配置和限制，不是把模板数直接当作题数。
- 服务端再次校验所有参数。前端可用性提示不能替代实际生成校验。
- 生成顺序：候选模板选取 → 参数生成 → 数学正确性检查 → 语义去重 → 整卷校验 → 一次事务保存。
- 同一模板可以换参数重复使用，但应限制连续重复套路；“同卷不重复”与“跨试卷绝不重复”分开，建议一期只保证前者。
- 按训练目标定义同题签名：只换选择项顺序、人物名或物品名不算不同数学题；交换因数是否视为同题，按是否考查交换律等训练目的确定。
- 有限次数重试仍失败，返回原因和推荐配置，不保存半张试卷，不自动跨难度补齐。
- 连点生成或网络重试采用幂等请求标识；主动“再来一份”使用新标识。
- 成功保存后预览/刷新/重打都读取快照，不重新随机生成。

## 5. 内容质量与模板管理

内容范围改为小学四年级数学上下册；按教材章节、独立知识点与训练目标拆分。候选知识清单与模板例子见 `四年级数学 · 知识点与模板维护设计.md`。原稿每知识点 6–9 个模板的数量不能作为全册估算。

每个模板需要：训练目标、题型、难度依据、参数约束、题干结构、标准答案、解析步骤、选择项生成规则、模板版本。

质量检查不止是“随机生成 100 次”：

1. 随机样本加固定边界样本：零与进位、舍入临界值、除法余数、小数位数、几何退化与刻度边界，按模板允许范围覆盖。
2. 数学检查：计算与单位一致，除数不为零，余数范围正确，数值精度明确，图形与图表满足条件，缺数类题目按要求验证答案唯一性。
3. 选择题检查：四个选项语义不同、恰有一个正确选项、正确项位置合理变化。符号不同但数学等价仍算重复。
4. 解析检查：答案正确不等于推导正确。不能生成器和校验器调用同一段答案逻辑后称为独立验证；结合代入、不变量和不同求解路径。
5. 人工检查：每模板代表题与边界题都审题，检查教材适配、措辞、难度和纸面效果；需确认谁承担。

建议模板算法保存在代码中并经过测试；数据库保存展示信息、启停、版本和受控参数配置。后台不接受任意 Python 或任意可执行表达式。一期建议支持已有算法的模板配置编辑，配套发布前校验与版本记录。

## 6. 身份、历史与数据建议

### 6.1 匿名使用

用户无需注册。首次请求由服务端创建匿名主体并签发凭证；不允许凭任意 `X-Client-Id` 换取已有用户身份。

详细设计采用同源HttpOnly Cookie承载服务端随机会话，用户与管理员会话独立；明确有效期、续期、SameSite与CSRF。SQLite仅保存令牌hash，一期不采用JWT；未来小程序身份接口独立设计。

“同一浏览器保留历史”的准确含义是：同一站点且身份凭证仍有效；清理凭证、换浏览器或换设备后不能自动恢复。浏览器 UUID 不能解决跨设备问题。

每次读取试卷和记录均按服务端身份校验归属；不可因为 paperId 难猜就省略鉴权。分享不是默认公开链接；若一期需要分享，必须另定可见范围、有效期和撤销规则。

微信绑定放到二期：验证已有匿名身份和微信身份后绑定；已有多个账号时再处理归并，绝不凭前端提交的用户编号接管记录。

### 6.2 全期设计与一期数据结构

已确认原则：表与数据对象尽量按全部规划功能设计，减少后期反复修改。建议先交付全期实体关系图、数据字典和对象契约，再分别标记一期启用、后期启用、业务规则待定。全期逻辑设计与一期是否创建全部物理表分开决定。

优先稳定的结构建议：

- 用户主体与登录身份分离：内部 user_id 不随匿名、微信、手机号改变；身份绑定有独立关系，为多设备与多登录方式保留位置。
- 知识点与教材章节分离：通过映射关联，同一知识点可复用于不同教材。
- 题目、来源、模板版本与试卷内容快照分离：生成题与未来真题共用明确的内容结构，来源信息独立，历史试卷不受题目更新影响。
- 题目对象定义题干、选项、答案、解析、知识点、难度、来源与版本；对外响应对象与数据库表分离，避免内部字段变更直接影响前端。
- 文件、审核、练习作答/错题、会员、订单和支付记录作为独立领域设计，明确与用户、题目、试卷的关联，不把未来所有状态塞进核心表或单个 JSON。
- 预留 schema_version、模板/引擎版本和结构化内容版本；未来字段通过明确迁移管理，不承诺完全不改表。

一期使用的核心表候选如下；身份与教材映射等结构将在全期设计中补齐，不将此清单当作最终 DDL：

| 表 | 用途 |
| --- | --- |
| app_user | 匿名主体和生命周期 |
| knowledge_point | 独立知识点身份；配套教材版本、章节映射和训练目标表，详见维护设计 |
| question_template | 模板标识、版本、题型、难度支持、启停与受控配置 |
| paper | 所属用户、请求配置、生成状态/时间、引擎版本、幂等标识 |
| question | 已生成题目内容、答案、解析、参数、模板版本和归一化签名 |
| paper_question | 题目顺序与关联 |
| usage_log | 必要行为事件与去重标识，明确清理周期 |
| admin_user | 仅在一期需要后台时建立并初始化 |

试卷快照至少保存实际题干、选项顺序、答案、解析和排序；seed、gen_params 与模板版本用于追踪，不能替代快照。新版本模板不能改写旧试卷。错误试卷的撤下与提示方式需明确。

教材版本、章节与知识点不是天然的一棵永久树：同一知识点可能出现在多套教材。当前已有四年级新旧版适配需求，建议一期就通过章节映射复用知识点，而非直接复制题目。

file已纳入一期PDF链路；审核、会员/支付等后续模块纳入全期逻辑设计；是否一期创建物理表待模型评审后决定。浏览器打印意向仍不能因为预留了下载表就记成成功下载。生成、记录与事件按用户/时间建立必要索引，设置外键与唯一约束。保留周期与删除规则须确认；不默认永久保留，也不默认全表软删除。

## 7. 接口与统计建议

建议的用户端接口：匿名会话建立/续期、知识点与能力配置、生成试卷、读取本人试卷、本人记录分页、接收允许的行为事件、健康检查。原稿缺少匿名凭证入口；健康检查不返回数据库路径、配置或密钥。

生成接口需要明确非法配置、能力不足、限流、繁忙、超时的响应；读取接口定义凭证过期、无权访问、记录不存在和已过保留期行为。

建议事件口径：

| 指标 | 权威来源 | 注意 |
| --- | --- | --- |
| 生成成功数 | 服务端成功保存的试卷 | 前端不能通过发事件伪造成功记录 |
| 生成失败数 | 服务端生成结果日志 | 区分参数错误、能力不足与系统故障 |
| 预览次数 | 前端 preview 事件 | 可重复访问，事件传输重试需去重 |
| 打印意向次数 | 前端 print_intent 事件 | 仅记录网站打印按钮点击，浏览器菜单/Ctrl+P 不保证覆盖 |
| 使用者规模 | 活跃匿名主体数 | 不等于真实家长人数，清理凭证可能产生新主体 |

事件带独立 event_id 去重；用户归属和服务端时间不能信任前端自报。埋点失败不能阻止打印。统计按 Asia/Shanghai 汇总日期，存储时间统一使用北京时间（Asia/Shanghai，固定微秒精度及 +08:00；2026-10-27更新）。

一期可统计后端已生成保存的PDF数量，不统计用户已保存到设备、已实际打印、已完成练习等无法可靠观察的事实。浏览器 `afterprint` 也不能证明这些行为 [S1]。

## 8. 打印与答案方案建议

答案生成属于题目质量的一部分；“打印时是否带答案”建议作为输出选项，而不是决定是否生成标准答案。历史记录可切换“仅题目/题目+答案”，题目本身不变。默认是否勾选答案待确认。

建议答案页包含答案和必要步骤，参数题需有完整条件。若仅给最终答案，需确认这足以支持家长核对。

排版：A4、单栏、15mm 页边距；题目与选项尽量不跨页；按解答步骤分配留白；答案独立起页。长题无法整块放入一页时必须有明确拆分策略，不能只依赖 avoid 规则。

打印就绪：试卷数据加载成功、KaTeX 无渲染错误、所用字体加载和布局完成后才允许打印。`nextTick` 只覆盖其中一步 [S2]。控制公式输入与 KaTeX 信任选项 [S7]。

建议先承诺一个明确浏览器与操作系统组合的打印效果，再根据试用者设备扩展。手机可浏览不等于手机、微信内置浏览器和无线打印均验收通过。首批试用设备决定优先级。

验收样本覆盖全部题量档、长公式、最多解答题、答案开启/关闭、多页和重复打印；至少一次真实 A4 打印，检查裁切、留白、页数与公式字体。

## 9. 技术、部署与投入建议

候选技术路线仍可用 Vue + FastAPI + SymPy + SQLite；是否需要双 Vue 应用取决于后台范围。Element Plus 等具体库不作为这一轮必须由用户逐项决定的问题。

建议先用独立构建目录，不引入额外仓库编排工具。代码名确定后，三个部分可命名为 web、admin、api；是否独立 Git 仓库按实际协作需要决定。

SymPy 属于计算负载：不要直接在异步请求循环中执行可能长时间阻塞的运算；控制参数范围、尝试次数、执行时长和并发，避免堆积。执行隔离方案在原型测量后确定，不能将 async 等同于加速 [S6]。

1C1G、单 worker 先作为试验配置，不保证容量。先测一张最复杂试卷和小并发的耗时、峰值内存、失败率、数据库锁等待。若是计算慢，迁移数据库未必有帮助。

备份采用 SQLite 一致性在线备份；每日频次和保留 7 天是候选策略，还需异机副本及恢复演练。备份频次意味着潜在数据损失窗口，需要结合记录的重要程度确认 [S3][S4]。

上线前定义 HTTPS、管理员初始凭证、登录限流、生成限流、日志轮转、数据目录权限和错误日志脱敏。上线后的平台要求、备案与部署地区适配需届时按官方要求单独核验，不沿用原稿中的确定性承诺。

建议按里程碑排期，确认每周投入后再换算周数：

1. M0：首个训练范围、代表样题、答案样张和纸面留白确认。
2. M1：模板与整卷验证通过，完成一张实际打印样张。
3. M2：匿名身份、保存快照、历史记录和核心页面闭环通过。
4. M3：必要后台、部署、备份恢复和越权检查通过。
5. M4：目标家长实际试用，收集题目问题、打印障碍和是否再次使用的反馈。

### 模板逐个整理的统一交付格式

每个模板一份内容卡：稳定编号、知识点/训练目标、题型、适用难度、题干、参数范围、生成约束、答案与解析、去重与校验规则、纸面留白、代表样题、当前状态。挑战目标发生变化时可拆独立模板，不强行将每个模板做成三档。

## 13. 已核对的技术依据

- [S1：MDN afterprint](https://developer.mozilla.org/en-US/docs/Web/API/Window/afterprint_event)：事件可能在打印开始或打印预览关闭后触发，不能作为成功打印凭据。
- [S2：MDN Document.fonts](https://developer.mozilla.org/en-US/docs/Web/API/Document/fonts)：所用字体加载与布局完成可通过 fonts.ready 等待。
- [S3：SQLite Online Backup](https://www.sqlite.org/backup.html)：提供运行中数据库的一致性备份机制。
- [S4：SQLite WAL](https://www.sqlite.org/wal.html)：WAL 是数据库持久状态的一部分，不能随意与主文件分离。
- [S5：SQLite Isolation](https://www.sqlite.org/isolation.html)：写操作串行化；迁移判断应围绕实际写入与等待，而非累计用户数。
- [S6：FastAPI 并发说明](https://fastapi.tiangolo.com/async/)：区分 I/O 并发与 CPU 计算负载。
- [S7：KaTeX Security](https://katex.org/docs/security)：控制不可信输入与 trust 选项。

本轮未做：竞品调研、市场需求验证、名称占用检查、平台准入和备案核验、服务器性能实测、代码实现。
