## 1. 分工原则

按模块归属分任务，不让每个终端各自实现一遍全站。每个任务必须有一个目录负责人；共享契约、迁移序列、依赖锁与入口集成由T0串行管理。以下路径为计划路径；详细设计中的泛化分层目录按本表细化，不要求已有代码迁移。

## 2. 先固定跨模块契约

T0先把03/04/05设计转成版本化DTO与接口样例，下面接口签名冻结后才并行实现：

- T1提供当前主体鉴权依赖、`check_generation_admission(session, user, now)`；不自行提交事务，由T4在受理事务完成job插入，在最终成功事务调用T1的record_generation_success写入600秒冷却。幂等检查在额度服务前执行。
- T2提供已发布不可变模板集合、数量策略、内容epoch及发布状态读取；不在内容模块另写一套出题器。
- T3提供registry、supports、generate、validate、semantic_signature；输入输出无数据库连接，异常映射到统一错误码。
- T4提供能力组合、生成任务、试卷快照与历史API；预览/验证也调用统一worker，不新建后台无界线程池。
- T5维护共享渲染器和tokens；T6仅提交使用需求，不能自行拷贝后修改另一份题目渲染逻辑。

接口变更先由T0更新契约版本/样例并通知使用方，禁止通过复制一份私有DTO掩盖不一致。T4提供纯能力分配函数，T2发布校验复用，避免循环服务依赖；此接口在第一批契约中确定。

## 3. 开发波次

1. T0基础/契约；T3整理首批参数与样题；T5定义视觉tokens/渲染器契约。先能启动、迁移和渲染一份固定试卷。
2. T1/T2/T3/T5可按可用终端并行；T6拿共享组件契约后基于mock开发。API未完成不阻塞页面骨架，但mock通过不等于联调完成。
3. T4在已固定接口下开发，依赖模块可先用测试替身；随后接入真实会话、模板和生成器。T0顺序合并迁移和入口，前后端逐模块联调。
4. T7验证完整闭环，模块负责人修复；首批模板三档样题通过人工审题与实际打印才开放试用。

每模块优先完成一期必需路径；未来表的逻辑设计不等于必须同时开发对应功能。PDF已确认为一期必交付：T4负责渲染执行/资产恢复，T5负责共享打印页和下载入口，T0维护运行依赖，T7验收真实PDF，详见07。

## 4. 分支与冲突控制

- 开发时每终端一个独立worktree，例如 `/Users/eric/PycharmProjects/papr-worktrees/t3-engine`，分支 `feat/v1-t3-engine`；禁止多个终端写同一工作目录或切同一个checkout。
- T0维护集成分支 `integration/v1`，按依赖顺序整合。首次开发再检查远程状态，不覆盖用户已有提交。本轮没有创建分支或推送授权。
- 每个终端使用独立SQLite文件、generated目录与端口；不能把别的终端数据文件视为测试临时文件删除。
- 模块负责人修改本模块ORM，提交迁移需求/字段变更；T0统一生成和串行合并Alembic迁移，避免多个head。提交前检查迁移与模型一致。
- pyproject/锁文件、web/admin package及锁、公共schemas、共享配置只由T0改；需要依赖由模块提出，由T0一次性更新。frontend-shared仅T5改。
- 不全仓格式化、不顺手改别的模块。SQLite及-wal/-shm、generated、密钥、node_modules、构建产物和本地日志列入.gitignore。
- 一个提交对应一个模块的可评审变化；合并前更新集成分支、检查diff边界、运行模块检查，再由T0执行集成检查。不得为了通过检查删掉其他模块测试。

## 5. 每个终端领取与交接格式

领取：任务ID、分支/worktree、允许修改路径、只读依赖、契约版本、验收场景、明确不在本任务的功能。

交接：提交号、实际修改范围、契约变化、迁移需求、已运行命令及结果、未验证事项、已知问题及后续依赖。文档示例或mock结果不能写成生产功能已完成。

重要集成检查：600秒限制在事务内且持久化；历史不重新生成；能力来自组件与验证报告；模板停用立即生效；用户/管理端输出相同快照；SQLite崩溃恢复；正式文件不公开直链；真实A4样张与三档数学正确性。
