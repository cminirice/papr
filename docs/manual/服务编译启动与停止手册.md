# 纸上练服务编译、启动与停止手册

适用：当前 macOS 本机开发环境，工程目录 `/Users/eric/PycharmProjects/papr`。核对日期：2026-11-05。

## 1. 有哪些服务

| 服务 | 作用 | 本机地址／端口 | 构建产物 |
| --- | --- | --- | --- |
| 用户端 `web` | 选择练习、生成、历史、下载 | http://127.0.0.1:5173 | `web/dist/` |
| 管理端 `admin` | 内容维护、验证、审题、发布、统计 | http://127.0.0.1:5174 | `admin/dist/` |
| 后端 API | 登录、目录、任务受理、数据查询、文件下载 | http://127.0.0.1:8001 | Python直接运行，无单独打包要求 |
| 任务 worker | 草稿预览、批量验证、出题及PDF生成 | 无HTTP端口 | Python直接运行，依赖打印构建产物 |
| PDF打印资源 `print` | worker调用的共享排版代码 | 无独立服务、无需单独监听 | `print/dist/` |

SQLite是文件数据库，不需要启动数据库服务。当前方案不需要Redis或Celery。API与worker各运行一个进程。

**本机API用8001。** 8000此前由AgentGate占用，不要为了启动纸上练停止那个服务。旧README及示例配置中的默认8000不适用于这份本机操作流程。

## 2. 每个终端先做的准备

以下启动方式使用四个独立终端窗口。**每个窗口都先执行这一段**，再执行对应服务命令：

```bash
cd /Users/eric/PycharmProjects/papr
export PATH="/Users/eric/.local/node-v22.23.2/bin:$PATH"
set -a
. ./.env
set +a
export PAPR_API_PROXY_TARGET=http://127.0.0.1:8001
```

说明：

- 应用不会自动加载根目录`.env`，所以必须显式载入。以上只用于本项目可信的本地配置文件。
- 当前已有`.env`和运行数据，不要用`.env.example`覆盖它。
- Node要求22.12及以上的22版本；本机已使用22.23.2。Python使用项目的3.12虚拟环境。
- API和worker必须使用相同的数据库、PDF目录、限流密钥和PDF运行配置。
- 浏览器统一访问`127.0.0.1`，不要在`localhost`和`127.0.0.1`之间切换，以免Cookie不一致。

若是另一台机器首次安装，应先按实际路径建立`.env`；本机关键配置如下，供核对，不要重新初始化已有数据：

```dotenv
PAPR_DB_PATH=/Users/eric/PycharmProjects/papr/backend/var/papr.sqlite3
PAPR_GENERATED_ROOT=/Users/eric/PycharmProjects/papr/backend/var/generated
PAPR_RATE_LIMIT_KEY_PATH=/Users/eric/PycharmProjects/papr/backend/var/rate-limit.key
PAPR_API_PROXY_TARGET=http://127.0.0.1:8001
PAPR_PDF_NODE=/Users/eric/.local/node-v22.23.2/bin/node
PAPR_PDF_BROWSER="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"
PAPR_PDF_FONT="/System/Library/Fonts/Supplemental/Arial Unicode.ttf"
PAPR_USER_ORIGINS=http://127.0.0.1:5173,http://localhost:5173
PAPR_ADMIN_ORIGINS=http://127.0.0.1:5174,http://localhost:5174
PAPR_COOKIE_SECURE=false
```

`false`仅适用于本机HTTP。以上没有密钥值或管理员口令。数据库与业务时间固定使用`Asia/Shanghai`。

## 3. 依赖安装与编译

### 3.1 依赖安装：首次准备或依赖锁文件变化时

已安装好依赖时，日常启动无需重复安装。先执行第2节的终端准备。

前端及PDF依赖在根目录统一安装：

```bash
npm ci
```

后端已有虚拟环境时，按锁文件同步依赖：

```bash
uv pip sync --python backend/.venv/bin/python backend/requirements.lock
```

只有`backend/.venv`不存在时，才先创建：

```bash
uv venv --python 3.12 backend/.venv
```

这里使用`backend/requirements.lock`，不是`uv sync`；前端使用根目录的`package-lock.json`，不要分别在web/admin安装另一套依赖。

### 3.2 一次构建全部前端和打印资源

```bash
npm run build
```

依次执行类型检查、用户端构建、管理端构建、打印资源构建。此命令只生成文件，**不会启动服务**。

### 3.3 按模块单独构建

| 目标 | 在项目根目录执行 |
| --- | --- |
| 前端类型检查 | `npm run typecheck` |
| 用户端 | `npm run build -w @papr/web` |
| 管理端 | `npm run build -w @papr/admin` |
| PDF打印资源 | `npm run build:print` |

单模块构建不包含根级类型检查；需要时先执行`npm run typecheck`。两个前端的开发服务直接使用源码，日常开发不必先生成dist。

**worker依赖已构建的打印资源。** 修改打印代码或共享题目渲染器后，应在没有任务执行时停止worker，执行`npm run build:print`，再启动worker。不要在出卷过程中替换打印资源。

### 3.4 后端检查与数据库升级

Python后端无需像前端一样编译打包。可选语法编译检查：

```bash
backend/.venv/bin/python -m compileall -q backend/app scripts/worker.py
```

这只检查语法，不代表业务测试或PDF验收通过。

更新代码包含数据库迁移时，在备份并停止API、worker后执行：

```bash
backend/.venv/bin/alembic -c backend/alembic.ini current
backend/.venv/bin/alembic -c backend/alembic.ini upgrade head
```

普通重启不需要重复初始化管理员、导入种子或重建数据库。备份说明见[本机试用](../implementation/本机试用.md)。

## 4. 启动：推荐四个终端分别运行

启动前先按第6节确认没有同一服务在运行。推荐顺序：API → worker → 用户端 → 管理端。四个窗口均执行第2节准备命令。

### 4.1 终端一：后端API

```bash
backend/.venv/bin/uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8001 --no-proxy-headers
```

看到`Application startup complete`及8001监听信息后，说明API已启动。这条命令不启用热重载；修改后端代码后需要停止并重新启动。

### 4.2 终端二：任务worker

首次启动前，确保已经执行过`npm run build:print`或`npm run build`。

```bash
backend/.venv/bin/python -u scripts/worker.py
```

启动时会做真实PDF渲染、解析、保存及回读探针。出现以下信息才表示该探针通过：

```text
PDF真实探针通过，用户worker就绪
```

之后还需要进程持续运行、心跳有效。新工作流的样例、验证和用户出卷均要求PDF运行环境就绪。只启动API和两个页面是不够的。

不要给常驻服务加`--once`，它最多处理一个任务后就退出。不要重复启动第二个worker。

### 4.3 终端三：用户端

```bash
npm run dev:web
```

访问：http://127.0.0.1:5173 。

### 4.4 终端四：管理端

```bash
npm run dev:admin
```

访问：http://127.0.0.1:5174 。

两个命令已经固定host、port和strictPort，**无需追加`--host`或`--port`**。端口被占用时会报错，不会自动换端口。页面代码修改通常自动热更新；代理目标等环境变量变化需要重启对应前端服务。

## 5. 停止与重启

### 5.1 本次在前台启动的服务

在对应终端按 **Ctrl+C**，等待进程退出、出现命令提示符：

| 服务 | 停止方式 | 重新启动 |
| --- | --- | --- |
| 用户端 | 用户端终端Ctrl+C | `npm run dev:web` |
| 管理端 | 管理端终端Ctrl+C | `npm run dev:admin` |
| API | API终端Ctrl+C | 第4.1节命令 |
| worker | worker终端Ctrl+C | 第4.2节命令 |
| 打印资源 | 无常驻进程可停止 | 需要更新时重新构建 |

计划停机时先确认后台生成记录中没有执行中的任务、模板验证也已结束，再停止服务；本机可按两个前端 → API → worker的顺序关闭。worker收到Ctrl+C或SIGTERM会退出并撤销就绪状态，但**不是保证等待当前任务完成的排空操作**。执行中断可能留下租约，重启后需要等待租约到期及有限重试。

重启就是“停止 → 按需构建/迁移 → 再启动”。关闭后启动不需要清空数据库、删除PDF或重设管理员。

### 5.2 原终端找不到，或服务由之前的会话启动

先找监听进程：

```bash
lsof -nP -iTCP:5173 -sTCP:LISTEN
lsof -nP -iTCP:5174 -sTCP:LISTEN
lsof -nP -iTCP:8001 -sTCP:LISTEN
```

worker没有监听端口，按命令查找：

```bash
pgrep -fl 'scripts/worker.py'
```

记下要停止的PID，先核对命令及工作目录。下面的`12345`必须替换成刚查到的真实PID：

```bash
ps -p 12345 -o pid=,ppid=,command=
lsof -a -p 12345 -d cwd
```

确认是本项目的进程后，发送正常终止信号：

```bash
kill -TERM 12345
```

等待退出，再重复查询确认。前端若是npm启动的子进程，应同时留意原npm进程是否已退出。**不要使用`killall node`、`killall python`或按8000端口杀进程**，会影响其他项目。历史日志存在并不说明对应进程还在运行；PID也可能被系统复用，每次都需核对。

## 6. 状态检查与常见问题

### 6.1 API与页面响应

```bash
curl --fail --show-error http://127.0.0.1:8001/api/v1/health
curl --head --fail --show-error http://127.0.0.1:5173/
curl --head --fail --show-error http://127.0.0.1:5174/
```

API健康接口只说明进程存活，不检查迁移、内容开放或worker。页面HTTP成功也不代表PDF能生成；完整确认需要worker探针通过，再用已发布内容实际生成并下载两份PDF。

### 6.2 PDF问题

只检查Chrome能否启动：

```bash
npm run pdf:probe -- --browser "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"
```

若结果是`browser_ready`，但`pdf_checked:false`，只代表浏览器就绪，**不是PDF生成验收通过**。

需要进一步生成并解析开发样张时：

```bash
backend/.venv/bin/python scripts/check_pdf_sample.py --node /Users/eric/.local/node-v22.23.2/bin/node
```

该命令会构建打印资源并生成开发样张，因此先停止worker、确认无任务执行，再运行；完成后重新启动worker。开发样张解析成功也不替代人工审题和A4排版检查。

### 6.3 问题对应处理

| 现象 | 检查与处理 |
| --- | --- |
| `npm: command not found`或Node版本不符 | 执行第2节PATH设置，用`node --version`核对 |
| `.env: No such file` | 确认进入项目根目录；已有本机配置不要覆盖 |
| 端口已占用 | 按第5.2节确认是否本项目已启动，避免重复启动 |
| 页面打开，但请求502／连接失败 | 检查API8001及前端代理目标，修改变量后重启前端 |
| 生成提示服务尚未就绪 | 检查worker是否仍运行、PDF探针是否通过，以及API/worker配置是否一致 |
| worker提示PDF配置不完整 | 核对Node、Chrome、字体路径和`print/dist/`构建产物 |
| worker提示运行资源变化 | 停止worker，完成构建/资源变更后重新启动；配置变更同时重启API |
| 用户端没有可用模板 | 属于内容开放条件，不能靠重启解决；按后台手册核对目录、组件、模板验证与发布状态 |

本机旧日志可在`backend/var/services/`查看；本手册的前台启动方式直接在终端显示日志，不会自动写入该目录。

## 7. 日常最短流程

1. 先检查服务是否已经在运行；运行正常时无需重复启动。
2. 首次或打印代码更新后，在停worker的情况下执行`npm run build`。
3. 开四个终端，每个执行第2节准备，再分别执行第4节四条启动命令。
4. 确认worker输出“PDF真实探针通过，用户worker就绪”。
5. 浏览器打开用户端5173、管理端5174。
6. 停止时等待任务结束，在对应终端按Ctrl+C；找不到终端则按第5.2节核对PID后停止。

这些是本机开发/试用操作，不是公网生产部署方案。`web/dist`和`admin/dist`构建成功后不会自动被API托管，正式部署仍需静态资源服务、API路由、HTTPS与进程托管配置。
